# Public contract changes

Canonical ISessions creation takes caller SessionId; IRequests submission takes caller RequestId separately from SubmitRequest payload. CQRS commands carry the same IDs and facades forward them unchanged. Empty and duplicate IDs reject before effects; no auto replacement. Caller recovery queries exact IDs and compares immutable context/submission fingerprint.

SessionRuntime exposes a typed targeted-dispatch command in HostControlled mode. Automatic scheduling and explicit target dispatch share the same atomic store policy; incorrect mode/target cannot fall back to another queued request. Mode persists in format2 and is checked before recovery/start. Controlled shutdown preserves queued input.

The framework package adds its own qualified typed outcome and invocation-context contracts using public AIAgent/AgentSession/AgentRunOptions APIs. Microsoft Agent Framework remains an unmodified external NuGet dependency. No internal framework access, fork or upstream patch is required.

Typed outcome admission validates declared state/certainty/output/continuation consistency and pending/background flags before serialization. Native session observation commits separately from stable framework session binding. Captured output and known termination are not erased by missing continuation.

## Typed outcome, invocation and evidence surface (T005)

- `FrameworkAgentOptions.QualifiedOutcomes` (default false) and `MaximumObservations` (default 16, nonnegative; 0 forbids agent-reported observations).
- `FrameworkExecutionOutcome`: recognized only as the exact CLR `AgentResponse.RawRepresentation` of a qualified registration. A typed NotStarted after an acknowledged operation or native session observation is Unknown.
- `FrameworkInvocation.TryGet(AgentRunOptions?)`: the adapter passes the context on its own run options as a typed member, not in `AdditionalProperties`. A clone of those options (`AgentRunOptions.Clone`) carries the same context. A context placed in `AdditionalProperties` is not recognised: this is a behavioural change from 0.2.0-alpha.8. The published 0.2.0-alpha.8 packages still write the context to `AdditionalProperties` and read it from there; the typed carrier exists only in this source (version 0.2.0-alpha.9, not published). The reason is that a chat-client agent copies run-option additional properties into the chat options it sends, which made the context, with its SDK identities, reach chat clients and their serialized requests (`UnitTests/FrameworkChatClientIsolationTests`). It is a transient context with `ObserveOperationAcceptedAsync` (once per invocation), `ObserveNativeSessionAsync` (first value fixed) and `ReportProgressAsync`; identities are nonblank and at most `MaximumReferenceCharacters` (512). Callbacks are awaited, deadline-bound and refused after the invocation returned.
- `ProviderObservationKind.InvocationPrepared` and `NativeSessionObserved` are new members. Only the framework adapter emits InvocationPrepared; for other adapters `ExecutionEvidence.InvocationPrepared` is false by construction and means only "not recorded". Third-party `ISessionStore` implementations must persist or explicitly refuse these kinds; refusal makes framework dispatches fail before invocation.
- `RequestSnapshot.Evidence` (`ExecutionEvidence`): public store reads, lists and cancellation results project it from the stored dispatch envelope; it is null before dispatch reservation. Stored snapshot copies are refused. Store implementers must project it on every public request read.
- `SessionBlockReason.ProviderUnavailable` together with `SessionSnapshot.ConfigurationUnavailable` and `AvailabilityError` records persisted **state**, not a proven cause.
  - SDK writers of `ProviderUnavailable` in normal operation:
    - Completion: `ISessionStore.CommitCompletionAsync` applies `SessionBindingPolicy.AfterCompletion`. Unless the session is `RecoveryRequired`, a committed reply with `ContinuationAvailable == false` or error `ProviderSessionExpired` sets `ProviderUnavailable`. The store accepts such replies as `ConfirmedEnded` or `NotStarted`. `ConfigurationUnavailable` and `AvailabilityError` are not changed; on a session without a configuration block they stay false and null. The reply error is stored on the request result, not on the session.
    - Dispatch registration mismatch: when a session's provider is not registered, or its binding's adapter or format version differs from the registration, `RequestDispatcher` commits `Failed`, `NotStarted`, `InvalidConfiguration` with `ContinuationAvailable == false` through the same completion commit. The session gets the same shape as above. This is not a confirmed end, no provider was invoked, and it is not the configuration pathway.
    - Configuration: `SessionAvailabilityPolicy.ForConfiguration`, applied through `ISessionStore.CommitConfigurationAvailabilityAsync`, records an unavailable registration with `ConfigurationUnavailable == true` and an `AvailabilityError`. It sets `ProviderUnavailable` only when the reason was `None`.
  - What a store caller can write, separately from those paths: on SQLite, the public `ISessionStore.MarkSessionBlockedAsync(sessionId, reason)` replaces any reason other than `RecoveryRequired` with the passed one and changes neither `ConfigurationUnavailable` nor `AvailabilityError`. With `ProviderUnavailable` it produces the completion shape without any continuation or registration being involved; with `None` it removes a `ProviderUnavailable` block. The SDK itself passes only `RecoveryRequired` (`SessionCatalog`).
  - `ProviderUnavailable` with `ConfigurationUnavailable == false` and no `AvailabilityError` therefore proves neither a lost continuation nor a confirmed end nor a registration mismatch.
  - Revalidation eligibility: a successful configuration check clears `ProviderUnavailable`, the flag and the error only while `ConfigurationUnavailable == true`. A block with the flag false is left unchanged. The rule decides which block the check may clear; it does not record why the block was set.
  - Recovery: at runtime start, `RecoveryCoordinator.PrepareAsync` reopens a session's provider binding only when the reason is `None`, or `ProviderUnavailable` with `ConfigurationUnavailable == true`, and then commits the configuration result. A `ProviderUnavailable` block with the flag false is therefore not reopened and not cleared at start, for every provider. Separately, `FrameworkSessionProvider` implements only `ISessionProvider` (no `ISessionAvailabilityProvider` or `IExecutionRecoveryProvider`). This describes start-up revalidation, not a lifetime guarantee for `BlockReason`: a successfully committed uncertain execution sets `RecoveryRequired` (`UnknownTransactions.Apply`), and explicit recovery decisions can change the block again (`RecoveryDecisionTransactions`).
  - Pinned by `IntegrationTests/ProviderBlockProvenanceTests` (completion, public setter and configuration shapes on SQLite across a reopen, and revalidation eligibility) and `UnitTests/SessionAvailabilityTests`. The dispatch-mismatch writer is described from source; that test does not exercise it.
  - Decision (T009, root choice C): no further block reason, no derived cause property, no API change; the persisted format is unchanged.
